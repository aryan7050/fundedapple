FUNDAPPLE BACKEND GUIDE (MATCHED TO CURRENT PROJECT STATUS)
==========================================================

This project is not a full enterprise SaaS yet. Right now, the workspace is mostly a static marketing site plus dashboard UI, not a live product backend.

So the correct approach is a practical MVP backend that fits the current status and can be expanded later.


1. CURRENT PROJECT STATUS
-------------------------
What already exists in this repo:
- landing page and marketing sections
- login page
- create account page
- forgot password page
- payment and checkout pages
- dashboard HTML layout
- various static pages like terms, refund, risk disclosure
- some JavaScript for UI interactions and localStorage-based saving logic

What does not exist yet:
- real database
- real user authentication
- production payment handling
- real challenge/account lifecycle
- orders and billing records
- payout approval system
- admin management
- email verification flow
- API layer connecting frontend to real data

This means the project is currently at the stage of: frontend-ready, backend-not-started.


2. BEST BACKEND CHOICE FOR THIS PROJECT RIGHT NOW
--------------------------------------------------
Use a simple but real stack:
- Backend: Node.js + Express.js or NestJS
- TypeScript: yes, preferred
- Database: PostgreSQL
- ORM: Prisma
- Auth: JWT + refresh tokens
- Payments: Stripe (primary, simplest) or Razorpay if local market needs it
- Email: Resend or SendGrid
- Cache: Redis (optional but useful)
- Hosting: Docker + VPS / Render / Railway / DigitalOcean

Recommendation for this exact repo:
- Express + TypeScript + Prisma + PostgreSQL + JWT + Stripe

Why this fits:
- easier for a static HTML/CSS frontend to connect to
- lighter than building a heavy enterprise stack from day one
- enough for a real funded challenge platform MVP
- easy to upgrade later into a larger structure

Do not overbuild with a giant microservice architecture at this stage. This repo is not at that level yet.


3. MVP GOAL
-----------
The first backend version should support only the essential business flow:
- user signup and login
- email verification
- plan list and pricing
- create order and checkout session
- successful payment confirmation
- issue funded account / challenge account
- dashboard summary API
- user payout requests
- admin review of payouts
- basic support tickets

This is the correct minimum set to make the project work like a real product.

6. AUTH MODULE
--------------
This is the first required backend feature.

Endpoints:
- POST /api/auth/signup
- POST /api/auth/login
- POST /api/auth/logout
- POST /api/auth/refresh
- POST /api/auth/verify-email
- GET /api/auth/me

Requirements:
- hash password using bcrypt or argon2
- use JWT access token
- store refresh token in DB or secure cookie
- validate email format
- check duplicate account creation
- allow role-based access (user/admin)
- protect user routes through middleware

This is where you convert the static login and create account pages into real app flows.


7. PLAN AND PRICING MODULE
--------------------------
The frontend currently has a challenge configurator and size selection logic.

Backend API should be the single source of truth:
- GET /api/plans
- GET /api/plans/:id
- POST /api/plans/preview

Plan data should not be hardcoded in frontend. It must come from database or admin config.

The backend will provide:
- price
- account sizes
- target %
- max drawdown
- daily loss rules
- minimum days
- reset option

This is important because the dashboard and checkout pages need a trusted source of pricing.


8. ORDER + PAYMENT FLOW
-----------------------
This is the real business engine.

Flow should be:
1. user selects a challenge plan
2. backend creates an order
3. backend creates Stripe checkout session
4. user pays
5. Stripe webhook confirms payment
6. backend updates order status to paid
7. backend creates or activates the challenge account
8. frontend shows success and dashboard entry

Endpoints:
- POST /api/orders/create
- GET /api/orders/:id
- GET /api/orders
- POST /api/payments/create-checkout
- POST /api/payments/webhook
- GET /api/payments/status/:id

Important rules:
- do not trust frontend price values
- verify webhook signature before marking payment successful
- always keep a payment log
- save transaction id and status

This is mandatory for a real platform.


9. ACCOUNT LIFE CYCLE
---------------------
After order is paid, create a user account record.

Account states:
- pending
- active
- phase1
- phase2
- funded
- failed
- breached
- cancelled

The account should track:
- current phase
- balance
- profitability
- drawdown
- min trading day rules
- reset eligibility

This is the core of the prop-firm business, and it should be a backend responsibility.

If you do not do this, the dashboard remains fake even if the UI looks polished.


10. DASHBOARD API
----------------
The dashboard is already designed, so the backend should expose real data to it.

Endpoints:
- GET /api/dashboard/summary
- GET /api/dashboard/accounts
- GET /api/dashboard/transactions
- GET /api/dashboard/payouts
- GET /api/dashboard/notifications

Dashboard data should include:
- current status
- funded balance
- challenge progress
- profit metrics
- payout history
- account health
- recent activity

At this stage, dashboard logic should be connected to the API and not rely on dummy data.


11. PAYOUT MODULE
-----------------
This is essential for a funded account platform.

Endpoints:
- POST /api/payouts/request
- GET /api/payouts/history
- PATCH /api/payouts/:id/status
- GET /api/payouts/eligibility

Requirements:
- only funded users can request payout
- verify payout eligibility rules
- store admin decision trail
- prevent duplicate payout requests
- log every payout action

This is one of the major business features after auth + payment.


12. SUPPORT + ADMIN MODULE
-------------------------
Basic support module:
- POST /api/tickets
- GET /api/tickets
- GET /api/tickets/:id
- PATCH /api/tickets/:id

Admin module:
- GET /api/admin/dashboard
- GET /api/admin/users
- GET /api/admin/orders
- PATCH /api/admin/payouts/:id
- PATCH /api/admin/users/:id/status

This is needed for real operations, not only front-end content pages.


13. SECURITY MUST-HAVES
-----------------------
Even in MVP, these are required:
- bcrypt password hashing
- JWT access tokens
- refresh token rotation
- CORS configuration
- request validation
- rate limiting on login/register routes
- environment variables for secrets
- webhook signature validation
- role-based access for admin routes
- logs for payment and payout actions

This project handles real money, so security is not optional.
